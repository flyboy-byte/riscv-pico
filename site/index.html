riscv-pico

A Raspberry Pi Pico running real Linux. The RP2040 emulates a RISC-V CPU, SPI PSRAM stands in for system memory, and the Linux guest reaches back out to drive physical pins.

A $4 microcontroller with 264 KB of RAM and no memory management unit, hosting a 16 MB Linux machine that boots to a shell, edits files in nano, and lights an LED from a shell command.

What it is

Core 1 of the RP2040 runs a full RV32IMA interpreter. Two SPI PSRAM chips stand in for system memory, and an SD card holds the kernel and root filesystem. Linux 6.6 boots on top of that.

The part worth caring about is not that Linux boots. It is that the emulated guest can reach real hardware. Typing echo 1 > /sys/class/gpio/gpio512/value into a shell inside the emulator ends with current flowing out of a physical pin.

Where the memory comes from

This is the trick the whole project rests on. The RP2040 has 264 KB of SRAM and the guest thinks it has 16 MB, so guest memory lives on two serial PSRAM chips and the RP2040's own SRAM becomes a cache in front of them.

The guest-to-firmware interface

Every capability the guest has beyond raw computation is a custom control register. The emulator core falls through to a handler for any register it does not recognise, which is why most of these needed no changes to the vendored emulator at all.

Why this shape was kept The framing that stuck is that this is not "Linux boots on a Pico" so much as a paravirtualised RISC-V machine hosted by an RP2040. Linux sees standard subsystems, a real gpiochip with the GPIO_V2 uAPI rather than a bespoke character device, and the custom transport stays underneath where userspace never meets it. That is what lets stock libgpiod tools work unmodified.

How it got here

Roughly four weeks from a vendored checkout to a standalone machine with its own keyboard and screen. The dates are the order things were actually proven, not planned.

2026-08-15Desktop harness boots to a shell. The real emulator core compiled against stand-in hardware headers, so every later change could be tested without a Pico.
2026-08-15Cross-compiler built and proven. Compile, inject into the rootfs, boot, run. Roughly two hours of build for a toolchain that has been reused ever since.
2026-08-16GNU nano runs. A real full-screen editor, which meant terminal handling and the C library were genuinely correct rather than approximately correct.
2026-08-25Both PSRAM chips graded good. The firmware's own JEDEC ID check turned out to be the fastest way to grade hand-soldered parts.
2026-08-27First Linux boot on real hardware. Two chips wired at once for 16 MB, SD card attached, shell on the Pico itself. nano ran and saved a file.
2026-08-29GPIO end to end. A shell command inside the emulator lit a physical LED, through a custom CSR, the emulator, and an RP2040 pin.
2026-08-29A power bug found and fixed. The OLED destabilised the PSRAM bus through a shared 3V3 node. Resolved with a separate supply and a single-point ground tie, which has been the template for every peripheral since.
2026-09-11PS/2 keyboard works. First real keyboard input to the emulated machine, with no firmware change needed. The driver was already compiled in and feeding the shared input queue.
2026-09-14VGA works, and the machine stands alone. Six jumpers to a breakout board, first picture on the first boot. Then USB unplugged, power from its own supply, and a file written in nano, saved and read back with no computer anywhere.

What's next

  • Terminal size on the VGA console. nano does not wrap on the 53×30 screen, most likely because the guest still assumes an 80×24 terminal. A one-line stty fix is the candidate and has not been tried yet.
  • First hardware run of the new SD image. The no-network kernel, Lua's sleep, c4 with for and write, and BASIC's exit command have only run in the desktop harness so far.
  • RP2350. Four board targets build clean. None have been flashed, so the claim stays marked unverified.

Explicitly not on the list: turning this into a framework, a build system, or a general-purpose emulator project. It is a bring-up and porting workbench and the scope fence is written into the repo.
